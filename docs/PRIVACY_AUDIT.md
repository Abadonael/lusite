  настройки не менялись, письма в поддержку не отправлялись. Пользователь не

## Решение T05

Для одного функционального значения темы баннер не добавлен. Смысл выбора —
именно запоминание оформления; subsequent read нужен для исполнения этого выбора.
На первом посещении читается только этот ключ для проверки существующего выбора;
автоматической записи системного предпочтения, обновления TTL, идентификатора
или профиля нет. Если storage запрещён, выбор действует без сохранения. Такая
узкая функция обоснованно рассматривается по исключению §25(2) №2 TDDDG.

**T05 целиком не закрыт**: NEL — отдельное хранение/чтение браузерной политики и
возможная передача данных; прямой пользовательский запрос на диагностику не
установлен. Предпочтительный следующий шаг — выяснить/отключить необязательный
NEL именно у pages.dev и повторить HTTP + browser-аудит. Не применены guessed
_headers/zone API: нет доказательств, что они отключат эту политику для проекта.
Если операция сохраняется и требует согласия, её надо блокировать до выбора,
обеспечить равноправный отказ и отзыв и проверять реальную сеть. Баннер в Hugo
не способен задним числом блокировать уже выданные edge-заголовки NEL.

## Недостающие проверки — точные действия

1. В отдельном чистом профиле Chrome/Edge открыть DevTools **до** первого перехода
   на https://kuranova.pages.dev/ru/. Network: Preserve log, Disable cache.
   Application: записать Cookies (включая HttpOnly/partitioned), Local/Session
   Storage, IndexedDB, Cache Storage и Service Workers до взаимодействий.
2. Переключить тему, язык, перезагрузить; повторить таблицы. Network: выписать
   только hostname/тип/инициатор и наличие Set-Cookie/NEL/Report-To. Не отправлять
   секретные значения, сырые HAR, содержимое писем или endpoint query. Отсутствие
   NEL-запроса при успешной загрузке не доказывает отсутствие отчётов об ошибках.
3. Cloudflare Workers & Pages → kuranova: production/preview build command,
   deployment SHA, Settings/integrations/Functions и Metrics→Web Analytics.
   Записать реально включённые сервисы и доступные log/security настройки.
   Для pages.dev не предполагать наличие своей zone. Нужны соглашение аккаунта,
   DPA и подтверждения support о неясных сроках/NEL.
4. Врач: тип почтового аккаунта, удаление писем/резервных копий и дополнительные
   технические доступы; медицинские данные не приглашать присылать через обычный
   email. Для будущей формы сначала определить получателя, канал, сроки и поля.

## Защита публикации и локальная проверка

Шесть страниц: content/{de,ru,en}/{impressum,datenschutz}.md, draft=true,
legalApproved=false; build.list=never. Они не попадают в список медицинских
статей/RSS. В локальной сборке есть реальные тексты и согласованные translationKey,
соответствующий HTML lang, общий footer и пометка черновика/noindex.

Обычная сборка исключает черновики и ссылки на них. Попытка собрать их с -D
в обычном environment останавливается errorf. Локальное ревью:

```powershell
hugo server --source hugo-site --environment legal-review --buildDrafts --destination C:\Nik\LuSite\.local\legal-review --bind 127.0.0.1 --port 1313 --disableFastRender
```

URL: http://localhost:1313/{de,ru,en}/impressum/ и /datenschutz/.
Не устанавливать legal-review или buildDrafts в Cloudflare. Черновой PR сам по
себе не публикует эти страницы; preview с обычной командой тоже их исключает.
Не выкладывать каталог локального ревью. Для выпуска сначала заполнить и проверить
тексты всех языков, затем снять draft и отметить legalApproved=true; проверить
обычную сборку и все footer-ссылки. До этого T03/T04 незавершены.
